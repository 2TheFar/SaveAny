# SaveAny 技术栈对比分析报告

生成时间：2026-05-06

## 1. 当前技术栈

当前项目已经实现的 MVP 使用的是：

| 模块 | 当前方案 |
| --- | --- |
| 前端 | Next.js 16 + React + TypeScript |
| 样式 | 原生 CSS |
| 后端 | Next.js Route Handlers，Node.js 调用 `yt-dlp` CLI |
| 核心下载能力 | 本机/服务器外部 `yt-dlp` + `ffmpeg` |
| 数据库 | 暂无 |
| 部署形态 | 前后端一体的轻量单体应用 |

当前方案的核心优势是：代码量少、部署简单、前后端在一个项目里，适合快速跑通 MVP 和小步迭代。

## 2. 候选技术栈

截图中的候选方案是：

| 模块 | 候选方案 |
| --- | --- |
| 前端 | Vue 3 + Vite + Tailwind CSS |
| 后端 | FastAPI + yt-dlp，Python，无数据库，轻量级 |
| 核心能力 | `yt-dlp`，支持大量网站 |

Context7 查询 FastAPI 文档后确认：FastAPI 适合构建高性能 Python API，天然支持类型提示、自动 OpenAPI 文档、WebSocket 等能力。官方全栈模板中也常见 Vite、TypeScript、Tailwind CSS、Docker 等组合。

## 3. 核心差异

| 维度 | 当前 Next.js 单体 | Vue/Vite + FastAPI 分离 |
| --- | --- | --- |
| 开发速度 | 初期最快，一个项目即可完成页面和 API | 前后端分离更清晰，但初始化和联调成本更高 |
| 部署复杂度 | 简单，一个 Node 服务即可 | 至少前端静态服务 + Python API 服务 |
| 前端体验 | React 生态成熟，Next.js 适合全栈 | Vue 3 + Vite 更轻快，前端心智更简单 |
| 样式工程 | 当前原生 CSS 可控，但长期维护容易分散 | Tailwind 更利于快速统一视觉规范 |
| `yt-dlp` 贴合度 | Node 调 CLI 可用，但深度控制一般 | Python 生态与 `yt-dlp` 更贴近，后续扩展更自然 |
| 下载进度 | 当前同步等待，体验一般 | FastAPI + WebSocket/SSE 更适合进度推送 |
| 类型与接口 | 前后端同项目，类型共享容易 | 需要维护 API 契约或生成客户端 |
| 长期扩展 | 适合轻量产品和快速迭代 | 更适合下载队列、异步任务、字幕、AI 总结等复杂后端 |

## 4. 是否值得迁移

短期不建议整体迁移。

原因：

1. 当前 MVP 已经跑通核心链路，整体迁移会消耗时间，但不会立刻提升用户价值。
2. 第一阶段目标是验证“公开视频链接保存”是否成立，Next.js 单体已经足够。
3. Vue/Vite + FastAPI 的优势主要体现在后续复杂任务，而不是当前单链接下载。

但候选方案有明显可借鉴之处，应该取长补短。

## 5. 建议借鉴的部分

### 5.1 借鉴 Tailwind CSS 的样式工程化

当前原生 CSS 可以继续用，但建议下一阶段考虑引入 Tailwind CSS 或至少沉淀一套类似 Tailwind 的设计变量。

建议优先级：高。

收益：

- 更容易持续模仿 `ai.codefather.cn/painting` 的统一视觉风格。
- 按钮、卡片、输入框、状态条可以形成统一设计语言。
- 后续页面增多时，比手写散落 CSS 更稳。

注意：Tailwind 不绑定 Vue，也可以直接用在 Next.js 里。

### 5.2 借鉴 FastAPI 的后端边界设计

当前不建议马上迁移到 FastAPI，但可以先按 FastAPI 思路重新规划后端边界：

- `info`：只负责解析视频元信息。
- `download`：只负责创建下载任务。
- `status`：查询任务状态。
- `file`：下载最终文件。

这样未来如果要把 Node 后端替换成 FastAPI，前端接口改动会更小。

建议优先级：中高。

### 5.3 下载任务复杂后再引入 Python/FastAPI

当出现以下需求时，再考虑拆出 FastAPI 下载服务：

- 下载进度实时展示。
- 多任务队列。
- 批量下载。
- 字幕提取和翻译。
- 视频总结。
- 长任务取消、重试、限速。
- 更细粒度地调用 `yt-dlp` Python API。

建议优先级：中。

### 5.4 保留当前 Next.js 单体作为产品壳

即使未来引入 FastAPI，也建议保留 Next.js 作为产品前端和轻量 BFF 层。

推荐演进方向：

```text
阶段 1：Next.js 单体 + yt-dlp CLI
阶段 2：Next.js 单体 + 更清晰的任务 API + Tailwind
阶段 3：Next.js 前端/BFF + FastAPI 下载服务
阶段 4：加入队列、数据库、账号、支付和 Pro 权益
```

## 6. 推荐结论

推荐策略：当前不迁移，逐步吸收候选栈优点。

具体建议：

1. 保留当前 Next.js + React + TypeScript 技术栈，继续作为 MVP 主体。
2. 下一阶段优先完善工作流文档、接口边界和任务状态，不急着重构。
3. 样式层可以考虑引入 Tailwind CSS，借鉴候选栈的前端工程化优势。
4. 后端暂时继续 Node 调 `yt-dlp` CLI；当出现队列、进度、批量、字幕、AI 总结时，再拆 FastAPI 服务。
5. 不建议切换到 Vue 3，除非团队更熟 Vue，或者你明确希望前端完全重写。

## 7. 下一阶段建议

建议下一阶段先做“技术方案文档化 + 接口边界重整”，而不是直接迁移技术栈。

阶段目标：

- 沉淀《SaveAny 技术架构方案.md》。
- 明确当前 MVP 的接口契约。
- 设计未来可切换 FastAPI 的后端边界。
- 决定是否在下一轮引入 Tailwind CSS。

这符合《实践原则.md》中的协同方式：先方案、再确认、后开发、最后验收。
