# SaveAny 第二阶段目标

生成时间：2026-05-06

## 1. 阶段定位

第二阶段不是直接大规模重构，也不是马上做正式商业版。

第二阶段目标是把第一阶段的 MVP 从“能跑通”推进到“架构边界清楚、平台策略清楚、下一步可持续开发”。

核心目标：

```text
从 yt-dlp 单一路径
升级为
平台识别 + 平台专用 Resolver + yt-dlp 通用兜底 + 后端代理下载
```

## 2. 关键判断

### 2.1 Next.js 的定位

Next.js 不需要被废弃，也不需要只当静态前端。

第二阶段建议让 Next.js 继续承担：

- 页面 UI。
- 产品工作台。
- 轻量 API/BFF。
- 与未来 FastAPI 下载服务通信。

但复杂下载任务、进度、队列和平台专用解析，后续应逐步沉到专门的后端服务中。

### 2.2 下载解析不能只依赖 yt-dlp

`yt-dlp` 仍然是重要通用能力，但不应该是唯一解析器。

当前已有测试证据：

```text
命令：
yt-dlp -j --no-playlist --no-warnings --skip-download https://www.douyin.com/jingxuan?modal_id=7630088455829370442

结果：
ERROR: Unsupported URL: https://www.douyin.com/jingxuan?modal_id=7630088455829370442
```

这说明该类抖音精选页链接不能直接交给 `yt-dlp` 处理，需要先做平台识别和抖音专用解析。

未来解析架构：

```text
用户提交链接
  ↓
平台识别
  ↓
Resolver 选择
  ├─ DouyinResolver
  ├─ BilibiliResolver（后续按需）
  └─ YtDlpResolver
  ↓
统一媒体信息模型
  ↓
后端代理下载 / 缓存 / 文件返回
```

## 3. 第二阶段重点任务

### 3.1 平台识别层

目标：

- 识别 YouTube、Bilibili、抖音、Vimeo、TikTok 等链接。
- 对短链进行安全解析，尤其是抖音分享短链。
- 将未知平台交给 `YtDlpResolver` 兜底。

验收标准：

- 输入常见平台链接后，能返回平台类型。
- 输入抖音短链后，能拿到最终跳转地址或明确失败原因。
- 不开放任意 URL 代理能力。

### 3.2 Resolver 抽象

目标：

定义统一 Resolver 接口，让前端不关心底层使用 `yt-dlp` 还是平台专用逻辑。

建议统一返回：

```text
title
duration
thumbnailUrl
platform
availableQualities
recommendedQuality
requiresCookie
resolverUsed
```

验收标准：

- `YtDlpResolver` 可覆盖当前已有能力。
- 后续可以独立新增 `DouyinResolver`，不影响前端调用方式。

### 3.3 抖音专用解析可行性验证

目标：

验证不拘泥于 `yt-dlp` 的平台专用方案是否可行。

验证范围：

1. 收集 3 到 5 个公开抖音分享链接。
2. 验证短链跳转。
3. 验证是否能提取视频 ID。
4. 验证 `douyin.com/jingxuan?modal_id=...` 这类精选页链接是否能转成真实视频信息。
5. 验证是否能无 Cookie 获取可播放地址。
6. 验证后端代理下载是否可用。
7. 记录失败类型：`yt-dlp` 不支持、需要登录、链接失效、接口变更、403/503、风控。

注意：

- 可以借鉴开源项目或第三方实现，但必须先核验 License、维护状态和安全风险。
- 不把平台私有接口细节散落到通用下载逻辑里，应封装在 `DouyinResolver` 内。

### 3.4 缩略图代理/缓存

目标：

解决当前前端直连第三方缩略图导致的防盗链问题。

推荐流程：

```text
解析得到 thumbnail
  ↓
后端请求图片
  ↓
缓存或转发
  ↓
前端加载 SaveAny 自己的图片地址
```

验收标准：

- 前端不直接使用第三方 thumbnail URL。
- 图片请求失败时展示默认占位图。
- 后端限制图片体积、超时和来源，避免开放代理风险。

### 3.5 真实清晰度展示

目标：

不要固定承诺 1080p，而是展示当前链接真实可用清晰度。

规则：

- 无 Cookie 可用最高 720p，则展示最高 720p。
- 如果 1080p 需要登录态，则提示“更高清晰度可能需要平台登录权限，当前默认不处理 Cookie”。
- 如果没有可下载格式，则返回结构化失败原因。

验收标准：

- 前端质量选项来自后端解析结果，而不是固定写死。
- 下载时按后端推荐格式或格式 ID 执行。

### 3.6 Cookie 策略

默认策略：

```text
公网版本默认不接收、不保存、不使用用户 Cookie。
```

原因：

- Cookie 接近登录凭据。
- 服务端处理 Cookie 风险高。
- 平台风控和合规风险高。
- 用户难以理解 Cookie 泄露后果。

例外：

| 场景 | 是否可评估 | 说明 |
| --- | --- | --- |
| 本地自用工具 | 可以 | Cookie 不离开用户本机 |
| 私有部署 | 可以 | 部署方自行承担凭据管理 |
| 公网 SaaS 默认能力 | 不建议 | 风险过高 |

第二阶段不实现 Cookie 下载能力，只在文档和错误提示中明确边界。

### 3.7 结构化错误

目标：

让用户知道失败原因，而不是只看到“下载失败”。

建议错误类型：

```text
INVALID_URL
UNSUPPORTED_PLATFORM
UNSUPPORTED_BY_YTDLP
NEEDS_LOGIN
NO_FORMAT
HOTLINK_BLOCKED
RATE_LIMITED
RESOLVER_FAILED
DOWNLOAD_FAILED
DEPENDENCY_MISSING
```

验收标准：

- API 返回结构化错误码。
- 前端按错误类型展示不同文案。

### 3.8 部署自检

目标：

启动时检查运行环境，避免用户点击下载时才失败。

检查项：

- `yt-dlp` 是否可用。
- `ffmpeg` 是否可用。
- 临时目录是否可写。
- 后端是否能访问外网。

正式部署建议：

```text
Docker 镜像内置 yt-dlp + ffmpeg
```

## 4. 暂不做的事情

第二阶段不做：

- 账号系统。
- 真实支付。
- 用户 Cookie 上传。
- 大规模批量下载。
- 长期文件存储。
- 数据库订单/额度系统。
- 承诺所有平台最高画质。

## 6. 验收标准

第二阶段完成时，应能回答：

- 当前链接属于哪个平台？
- 用哪个 Resolver 处理？
- 当前无需 Cookie 的最高可下载清晰度是多少？
- 缩略图是否已由 SaveAny 后端代理或缓存？
- 失败时用户能否知道原因？
- 未来是否能平滑接入 FastAPI 下载服务？

如果这些问题都有明确答案，第二阶段就算完成。
